# LAB: Graph Analysis for Fintech Fraud Detection
## From supervised and unsupervised techniques to hybrid scoring

**Duration:** 4–5 hours · **Level:** intermediate SQL / introductory ML · **Language:** English

This workshop accompanies `graph_fraud_hybrid_scoring_marp.md`. The supplied ChatGPT share URL could not be retrieved; the current matching presentation was read instead. The lab follows its central thesis: transaction models, anomaly signals, and relational evidence feed one decision layer. All accounts, transactions, labels, and results here are synthetic.

## Learning outcomes

By the end, participants can:

1. Model accounts, devices, and directed transfers as a property graph over relational tables.
2. Detect shared devices, fan-in, fan-out, time-ordered cycles, and bounded multi-hop paths.
3. Explain why these patterns also appear in legitimate activity.
4. Build transaction-only supervised and unsupervised baselines.
5. Add graph features and combine signals in a hybrid risk score.
6. Compare graph and non-graph variants on a later time period at a fixed review budget.
7. Prevent future-event, late-arrival, and label-availability leakage.

## Technology choice

| Track | Role | Trade-off |
|---|---|---|
| **DuckDB 1.4.4 + DuckPGQ** | Recommended property-graph exercises, SQL/PGQ pattern matching | Lightweight local setup; community-extension compatibility and downloads must be checked |
| **DuckDB SQL** | Fully runnable reference pipeline, feature extraction and recursive paths | Graphs expressed as joins and recursive CTEs; no extension needed |
| PostgreSQL + Apache AGE | Optional server-based follow-up | Requires extension installation and a supported PostgreSQL/AGE pairing; not implemented or tested in this package |

PostgreSQL does not gain AGE merely by upgrading PostgreSQL. AGE is a separate graph extension using openCypher. DuckPGQ adds SQL/PGQ to DuckDB. The official DuckDB graph guide currently specifies 1.4.4 rather than 1.5.x for DuckPGQ; this lab pins 1.4.4 accordingly. Check the linked documentation before changing versions.

The core lab deliberately uses standard SQL graph representations so it remains usable without an extension. Native property-graph syntax is an additional exercise, not silently substituted by Python graph processing. ML uses scikit-learn; no Neo4j dependency is included.

## Scenario and schema — 20 minutes

A fintech analyst wants to identify coordinated account networks while controlling false positives from family devices and legitimate payment hubs.

| Table | Important columns | Meaning |
|---|---|---|
| episodes | episode_id, day, cutoff | Daily decision snapshot |
| accounts | account_id, episode_id, age_days | Account vertices |
| transfers | src, dst, amount, event_time, observed_at | Directed payment edges |
| device_use | account_id, device_id, event_time, observed_at | Account-to-device edges |
| labels | account_id, y, label_available_at | Outcomes, disclosed two days after cutoff |

`account_id` is globally unique. Transfer tables allow repeated payments between the same pair; this is a directed multigraph. Counterparty degree uses `count(DISTINCT ...)` so repeated payments do not inflate distinct-neighbor counts. SQL/PGQ uses the device table as a second vertex type.

Generated cases include ordinary transfers, coordinated collection/dispersal, shared infrastructure, and ordered three-edge cycles. Some legitimate cases deliberately resemble fraud hubs. All members of a synthetic fraud case receive a positive label; real investigations rarely offer such complete labels. The generator's simple labels and strong motifs make this a teaching dataset, not realistic performance evidence.

**Exercise:** sketch the graph for account → device ← account and account → account → account. Identify which edge type is directed and which observations could be ambiguous.

**Checkpoint:** shared IP or device is supporting evidence, not proof of common malicious ownership. A two-hop path establishes connectivity, not tracing of identical currency units.

## Lab 1: Build a point-in-time graph — 25 minutes

Read `visible_transfers` and `visible_devices` in `features.sql`.

A record is usable only when both `event_time <= cutoff` and `observed_at <= cutoff`. An old event delivered tomorrow was unavailable today. The generator inserts two poison records per case: a future transfer and a late-arriving transfer. Neither may affect features.

Tasks:

1. Count raw and visible transfers; verify a difference of **1,800**.
2. Verify visible amounts are below 1,000 while raw data includes 999,999.
3. Remove only the observation-time predicate in a copy and inspect the inflated amount features.
4. Restore it before model evaluation.

**Submission:** two counts and a one-paragraph explanation of why filtering event time alone leaks information.

The lab computes one account risk score at each daily cutoff. It does not implement per-transaction online scoring or sliding historical windows. For production, also constrain a lookback window and rebuild each historical snapshot independently.

## Lab 2: Native property graph and motifs — 45 minutes

Run `duckpgq.sql` if the extension is available. It materializes filtered transfers/devices before declaring the graph. Do not declare a graph over the unfiltered input tables.

Tasks:

1. Query two accounts sharing a device. Use canonical ordering (`a < b`) and `DISTINCT` to remove symmetric/duplicate results.
2. Find directed two-hop payment paths, excluding a return to the original sender.
3. Add strictly increasing timestamps and a 30-minute bound. Compare the count with the unconstrained query.
4. Compare shared-device triples from SQL/PGQ with the first query in `answers.sql` using set equality, not only row count.
5. Describe what happens when a single account logs into the same device repeatedly.

Then inspect features for:

- Fan-in: at least five distinct senders.
- Fan-out: at least five distinct recipients.
- Device sharing: at least four other accounts.
- Ordered cycle: A → B → C → A within 30 minutes, with three distinct nodes.

The cycle feature flags the account initiating the ordered sequence. It does not label all three members. Random ordinary transfers can also form a cycle; do not assert an exact cycle count without inspecting the generated run.

**Checkpoint:** explain the difference between a directed cycle ignoring time and a temporally valid circular sequence. Even an ordered sequence does not prove laundering or value conservation.

## Lab 3: Multi-hop investigations — 25 minutes

Run the recursive CTE in `answers.sql`. It explores up to three hops, avoids revisiting a node within a path, and reports the shortest discovered distance for each origin/destination pair.

Tasks:

1. Change the maximum depth from three to two; explain which pairs disappear.
2. Select one account and extract its neighborhood rather than scanning the entire graph.
3. Add event ordering to the traversal by carrying the last timestamp in the recursive state.
4. Explain why the reference traversal is structural reachability, not temporal fund tracing.

At this scale recursion is convenient. Dense graphs can create huge intermediate path sets even with a depth bound. Measure query time before scaling; bound the seed set, time window and traversal depth.

**Optional extension:** build a table of confirmed-risk seeds with `known_at`, use only seeds known before cutoff, and compute exposure within two hops. Do not use the full labels table as if labels were already known. This extension is an exercise, not part of the tested reference model.

## Lab 4: Supervised and unsupervised baselines — 35 minutes

Inspect the explicit feature lists in `run_lab.py`.

**Transaction baseline:** age_days, total incoming amount and total outgoing amount. Logistic regression learns labeled account risk.

**Unsupervised baseline:** Isolation Forest fits the same three features on the mixed training population without looking at labels. Its anomaly score is mapped to [0,1] using the empirical training-score distribution. This is a rank-like anomaly indicator, not a fraud probability. Scores beyond the training range saturate at the ends.

**Graph features:** fan-in, fan-out, device peers, ordered cycle and pass-through amount ratio. The pass-through ratio has no explicit time-lag constraint beyond the daily snapshot; it must not be described as rapid pass-through.

Tasks:

1. Identify why account IDs, day, case identifiers and outcomes are excluded from model inputs.
2. Inspect an anomalous legitimate account and a low-anomaly positive account.
3. Retrain after removing account age. Assess whether the baseline was relying too heavily on the generator's age distribution.
4. Explain why normalizing an anomaly score is different from calibrating probability.

## Lab 5: Hybrid scoring — 35 minutes

Reproduce the presentation's illustrative formula:

`risk = 0.15*rules + 0.40*supervised + 0.15*anomaly + 0.30*graph_risk`

The runner uses [0,1] components; multiply by 100 for a display score. These coefficients reproduce the deck, not validated production weights. The amount rule and topology weights in the runner are also teaching heuristics.

The graph risk component combines capped fan-in, fan-out, shared-device and cycle indicators. It is intentionally interpretable. The fixed weighted sum is not a calibrated fraud probability.

Next, compare learned logistic stacking:

- Without graph: rule, transaction classifier, anomaly score.
- With graph: rule, graph-enriched classifier, anomaly score, topology risk.

Only the later calibration window trains the stacking layer. Its probability estimates are evaluated using Brier score; the lab does not assume perfect calibration. The two variants differ in both engineered graph inputs and the graph-enriched base model, so their difference measures the complete graph addition, not one isolated feature.

Tasks:

1. Calculate the deck example: 30, 45, 70, 95 → **61.5**.
2. Inspect at least three top queue entries and their reason codes.
3. Explain why reason codes describe observed patterns rather than formal model-attribution values.
4. Remove shared-device features from both classifier and topology score; rerun to isolate their contribution.

## Lab 6: Honest evaluation and decision policy — 35 minutes

| Stage | Days | Purpose |
|---|---|---|
| Train | 1–48 | Fit base models and anomaly reference |
| Embargo | 49–50 | Allow delayed training labels to mature |
| Calibration / tuning | 51–63 | Fit ensemble and review threshold |
| Embargo | 64–65 | Allow calibration labels to mature |
| Test | 66–90 | Final evaluation only: 2,000 accounts |

Models A–E in `results.json` compare rules, supervised baseline, hybrid without graph, hybrid with graph, and the presentation's fixed-weight hybrid. Average precision is a PR summary metric; report it as average precision rather than implying it is trapezoidal PR-AUC. Precision@50 and recall@50 use a **global budget of 50 accounts across the test period**, not 50 per day. Equal scores break ties by account ordering.

Separately, the review queue uses the calibration set's 90th percentile as its threshold. Its test volume can differ from 10% under distribution change and ties. It is not the same selection as the top-50 evaluation. No score triggers an automatic block in this lab.

Tasks:

1. Compare model C with model D at the same top-50 budget. State whether graph features improved this run.
2. Report average precision, precision@50, recall@50 and test prevalence together.
3. Check Brier scores for probability outputs; inspect calibration by probability bins as an additional exercise.
4. Write a short analyst decision on a suspicious legitimate hub using labels only after initial investigation.
5. Explain why synthetic lift does not establish production lift, prevented loss or customer impact.

A shuffled row split is unsuitable here: neighboring accounts from the same case could land on both sides. The provided time split also separates cases and identities. Repeated customers and known-network deployment would need additional evaluation designs. No fairness, latency or monetary-loss result is claimed by this workshop.

## Production follow-up, outside this lab

Add entity-resolution confidence, trailing windows, bitemporal corrections, persistent cross-day identities, tenant isolation, feature freshness, missing-signal behavior, explainability review, realistic label delays and monitoring. Compare simple graph features before adopting GNNs. A graph database or extension alone does not provide these controls.

For PostgreSQL, a follow-up workshop could use relational tables plus recursive CTEs, then Apache AGE for native graph queries. Use a release-supported PostgreSQL/AGE combination from the official download matrix; this package does not provide a tested AGE deployment.
